# Part 13：成本模型与 ROI 分析

> **面向角色**：需要量化推理成本、做技术选型的 TL/架构师  
> **目标**：建立 $/1M tokens 的成本计算框架，理解不同方案的经济性

---

## 13.1 成本构成

```
单次推理成本 = 硬件折旧 + 电费 + 运维人力 + 网络/IDC

按 token 摊销:
  $/1M tokens = (总成本 / 总产出 token 数) × 1,000,000
```

### 13.1.1 硬件成本

| GPU | 典型单价（美元） | 功率 | 适用场景 |
|-----|----------------|------|---------|
| A100-80G | ~$10,000-15,000 | 400W | 通用推理 |
| H100-80G | ~$25,000-30,000 | 700W | 高性能推理 |
| H200-141G | ~$35,000-40,000 | 700W | 大模型/长上下文 |
| B200 | ~$40,000-50,000 | 1000W | 下一代 |
| MI300X-192G | ~$20,000-25,000 | 750W | 大显存替代 |
| 昇腾 910B | ~$15,000-20,000 | 400W | 国产化 |

### 13.1.2 电费成本

```
电费 = 功率 × 时间 × 电价

示例: H100 × 1 台，24h 运行，电价 $0.1/kWh
  = 0.7 kW × 24 h × $0.1 = $1.68/天
  = ~$613/年

对于 1000 卡集群:
  功率 ≈ 700 kW
  年电费 ≈ $613,000
  加上 PUE 1.2 → ~$735,000
```

### 13.1.3 折旧成本

通常按 3-5 年折旧：

```
H100 年折旧 = $30,000 / 3 年 = $10,000/年/GPU
            = $833/月/GPU
            = $27/天/GPU
```

## 13.2 $/1M tokens 计算模型

### 13.2.1 输入/输出 token 分别定价

行业惯例：input tokens 比 output tokens 便宜，因为 input 只做一次 prefill，output 要多次 decode。

```
成本模型:
  每 1M input tokens 成本 = C_in
  每 1M output tokens 成本 = C_out
  
  一次请求成本 = (input_tokens / 1M) × C_in + (output_tokens / 1M) × C_out
```

### 13.2.2 计算实例

**场景**：70B 模型，8×H100 FP8，日产出 100M tokens。

```
硬件成本:
  8 × H100 = $240,000
  3 年折旧: $240,000 / 3 = $80,000/年
  年电费: 8 × 0.7 kW × 8760 h × $0.1 × 1.2 = ~$5,900
  年总成本 ≈ $85,900

$/1M tokens:
  年产出 = 100M × 365 = 36.5B tokens
  $/1M = $85,900 / 36,500 = $2.35 / 1M tokens

对比 OpenAI API GPT-4 定价 (~$30/1M output tokens):
  自建成本低约 10x（不考虑人力、网络、运维）
```

### 13.2.3 不同量化方案的成本对比

| 方案 | 单卡可服务 | 8×H100 并发 | $/1M tokens（估算） |
|------|-----------|------------|-------------------|
| FP16 | 7B | 70B 需 TP=8 | $4.5 |
| FP8 | 13B | 70B 单卡 | $2.3 |
| AWQ INT4 | 13B | 70B 单卡 | $2.0 |
| GPTQ INT4 | 13B | 70B 单卡 | $2.1 |

**注意**：INT4 虽然成本低，但可能带来精度损失和额外支持成本。

## 13.3 不同引擎的 TCO 对比

| 维度 | vLLM | SGLang | TRT-LLM | LMDeploy |
|------|------|--------|---------|----------|
| 单卡吞吐 | 中 | 高 | 很高 | 高 |
| 部署复杂度 | 低 | 中 | 高 | 中 |
| 人力成本 | 低 | 中 | 高 | 中 |
| 硬件锁定成本 | 无 | 无 | 高 | 低 |
| 综合 TCO（同等吞吐）| 中 | **低** | 中-高 | 低 |

**为什么 SGLang TCO 可能最低？**
- 更高吞吐 → 同样 QPS 需要更少 GPU
- 更好的 prefix caching → 减少重复计算
- 开源 → 无 license 费用

**为什么 TRT-LLM TCO 不一定最低？**
- 虽然单卡性能高，但部署和调优人力成本高
- 闭源导致问题排查困难
- NVIDIA 硬件锁定

## 13.4 ROI 决策框架

```
Step 1: 明确业务指标
  - 日均 token 量
  - 峰值 QPS
  - 延迟 SLA (TTFT/TPOT P99)
  - 可用性要求 (99.9% / 99.99%)

Step 2: 计算自建成本
  - GPU 数量 = peak_tokens_per_sec / per_gpu_throughput
  - 硬件采购 / 租赁成本
  - 电费 / IDC / 网络
  - 运维人力 (GPU × 0.1 FTE)

Step 3: 计算云服务/API 成本
  - OpenAI / Anthropic / Azure 定价
  - 预留实例折扣
  - 网络出口费用

Step 4: 考虑隐性成本
  - 自研：灵活性、数据安全、定制优化
  - 云服务：vendor lock-in、数据出境合规

Step 5: 决策
  - 量大且稳定 → 自建
  - 量小或波动大 → 云服务
  - 中间态 → 混合部署
```

## 13.5 成本优化策略

### 13.5.1 硬件层面

```
1. 量化: FP8/INT4 减少 GPU 数量
2. 二手/租赁: A100 二手或云租赁降低 CAPEX
3. 异构: P 节点用 A100，D 节点用 H100
4. 动态扩缩容: 按负载自动调整 replica 数
```

### 13.5.2 软件层面

```
1. Continuous Batching: 提高 GPU 利用率
2. Prefix Caching: 减少重复 prefill
3. 投机解码: 降低 decode 成本
4. PD 分离: 更合理的硬件分配
5. 合适的 batch size: 避免 TPOT 过度增长
```

### 13.5.3 调度层面

```
1. 多租户共享: 提高整体利用率
2. 优先级队列: 保障高价值请求
3. 自动 fallback: 峰值时降级到云服务
```

## 13.6 面试常见问题

**Q: 如何计算一个 LLM 推理服务的单位成本？**
- 答：先算总成本（硬件折旧+电费+人力+网络），再除以实际产出的 token 总数，得到 $/1M tokens。要区分 input/output，因为 decode 更贵。

**Q: 量化能降低多少成本？**
- 答：FP8 通常减少 40-50% GPU 需求（权重减半+可能更高吞吐），INT4 可减少 50-70%。但要权衡精度损失和工程维护成本。

**Q: 什么时候应该自建而不是用云 API？**
- 答：当月 token 量超过某个阈值（通常是 10B-100B，取决于模型大小），且负载稳定、对延迟/数据安全有要求时，自建更划算。

| 主题 | 关键点 |
|------|--------|
| 成本构成 | 硬件折旧 + 电费 + 人力 + 网络 |

| 量化收益 | FP8 省 40-50%，INT4 省 50-70% |
| TCO | SGLang/vLLM 开源方案综合成本低 |
| ROI 决策 | 量大稳定自建，量小波动用云 |
